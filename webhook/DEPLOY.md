1. Go to: https://supabase.com/dashboard/project/cpkyloywjmpesmjgqaxm/sql/new

## Step 2 — Supabase: Create the courses storage bucket

1. Supabase Dashboard → Storage → New Bucket
2. Name: `courses`
3. Public bucket: **Yes** (so PDF URLs work without auth)
4. Upload each course PDF: drag-and-drop the files from `/Users/mac/Documents/meridian-cpd/courses/`
   - The PDFs are generated by the `pdf_builder.py` script in `/courses/`
   - Filename must match: `MER-DEA-001.pdf`, `MER-DEA-002.pdf`, etc.

## Step 3 — Gmail: Get OAuth credentials

You need a refresh token so the webhook can send email as hello@meridiancpd.co.uk.

1. Go to: https://console.cloud.google.com/
2. Create a new project: "Meridian CPD"
3. Enable the Gmail API: APIs & Services → Enable APIs → search "Gmail API" → Enable
4. Create OAuth credentials:
   - APIs & Services → Credentials → Create Credentials → OAuth Client ID
   - Application type: **Web application**
   - Authorized redirect URIs: `https://developers.google.com/oauthplayground`
5. Note your **Client ID** and **Client Secret**
6. Get the refresh token:
   - Go to: https://developers.google.com/oauthplayground
   - Click the gear icon (⚙) → Check "Use your own OAuth credentials" → enter Client ID + Secret
   - In the left panel, find "Gmail API v1" → select `https://www.googleapis.com/auth/gmail.send`
   - Click "Authorise APIs" → sign in as hello@meridiancpd.co.uk
   - Click "Exchange authorization code for tokens"
   - Copy the **Refresh token**

## Step 6 — Stripe: Register the webhook endpoint

1. Stripe Dashboard → Developers → Webhooks → Add endpoint
2. Endpoint URL: `https://your-app.up.railway.app/stripe-webhook`
3. Events to listen to: `checkout.session.completed`
4. Click Add endpoint
5. Copy the **Signing secret** (starts `whsec_...`)
6. Add it to Railway Variables as `STRIPE_WEBHOOK_SECRET`

### After payment: send buyers to the app's thanks page

On **each** payment link (single course and annual subscription): Stripe Dashboard →
Payment links → the link → Edit → **After payment** → **Don't show confirmation page** →
redirect customers to:

```
https://app.meridiancpd.co.uk/thanks?session_id={CHECKOUT_SESSION_ID}
```

Type `{CHECKOUT_SESSION_ID}` exactly as shown; Stripe fills it in. The page shows the buyer
the address their course was sent to and lets them correct a typo once, within 7 days, which
sends everything again to the right address. For anyone who writes in instead, use
Admin → Members → Fix email. Deploy the app before changing the links, or buyers land on a
page that doesn't exist yet.

## Field Work series (one purchase, three courses)

A series is three courses sold together for £39.99. One checkout makes three purchase
rows, three completion links and three certificates; the price is recorded as £13.33 a
part. The series are defined in `SERIES` in `main.py`; a series whose courses are not all
in the catalogue is skipped at start-up and cannot be bought.

Set-up, in this order:

1. **Supabase, before deploying (hard rule):** run `migrations/2026-10-29_series.sql` in
   SQL Editor. It replaces the one-row-per-session rule on `purchases` with one row per
   course per session and adds `series_id` and `emailed_at`. Safe to run again.
   What happens if the app is deployed without it: a series purchase cannot be recorded
   at all (the first row's `series_id` has nowhere to go), so nothing is sent, the
   webhook answers 500 with the error in the Railway log, and Stripe retries the event
   into the same error for up to three days. The buyer has paid and has nothing until
   the migration is run, after which the next retry delivers all three parts. Single
   courses and subscriptions still work without it (their `emailed_at` mark is skipped
   with a log line), but do not rely on that.
2. **Stripe:** Products → Add product "Field Work series", one-off price £39.99 GBP.
   Create a Payment Link from it; on the link, collect the customer's name, and set
   After payment → redirect to `https://app.meridiancpd.co.uk/thanks?session_id={CHECKOUT_SESSION_ID}`
   as for the other links. Copy the price ID (`price_...`) to Railway as `STRIPE_PRICE_SERIES`.
3. **Stripe, promo codes:** restrict the MERIDIAN10 coupon to the £19.99 single-course
   product. The site does not pass a promo code on the series link, but a code typed at
   checkout applies to whatever product the coupon allows.
4. **Site:** paste the Payment Link into `STRIPE_SERIES` in `landing-page/courses.html`.
   The series button only shows when that is set and every part is on sale. The £39.99
   card on the home page pricing section is commented out until then (see the note in
   `index.html`).
5. **Decks:** a series course is delivered as a NotebookLM slide deck with the written
   course as notes. Upload each deck with `tools/upload_deck.py MER-ALL-019 deck.pdf`
   (it goes to Storage as `MER-ALL-019-deck.pdf`; the notes stay at `MER-ALL-019.pdf`,
   built from the markdown as usual). Then take the course out of `UNDER_REVIEW` in
   `main.py`, `landing-page/courses.html` and `landing-page/under-review.json`.
   Admin → System checks both files for every deck course on sale.

**Deploy window.** The app follows the site's `landing-page/under-review.json` (read
every ten minutes), and this change lists MER-ALL-019 to 021 there. Both the site (GitHub
Pages) and the app (Railway) deploy from `main`, so after merging check that
`https://meridiancpd.co.uk/under-review.json` lists the three courses before, or as soon
as, the Railway deploy finishes. If Railway finishes first and the site still serves the
old empty list, the app un-withdraws the three courses and subscribers see them in their
library with download links that 404 until the Pages deploy lands. If that happens, wait
for Pages and the app corrects itself within ten minutes, or restart the Railway service.

**How a series checkout runs.** The buy link carries the series id:
`<payment link>?client_reference_id=FW-INSULATION` (a Payment Link can carry
`metadata.series=FW-INSULATION` instead). For each part the app records the purchase row,
sends the email, then marks the row `emailed_at`. If anything fails part-way, the webhook
answers non-2xx and Stripe delivers the event again; the app then finishes only the parts
not yet marked, so no part is ever sent twice, and prints `ACTION NEEDED` so the buyer's
emails can be checked. A series payment the app cannot match to a series is recorded as
one row (`course_id` SERIES) with an `ACTION NEEDED` line and nothing is sent: work out
the series from the Stripe receipt and send each part with Admin → Test purchase (email
and course id; it records a £0 test row), or refund.

## Outreach from the app (Admin → Outreach)

The daily outreach email to the corporate contact list is sent by the app itself
(`webhook/outreach.py`), not by the old Node service in `Meridian/meridian-outreach`
(still deployed on Railway as `meridian-outreach`, idle; its campaign is `paused` and
must stay that way, or be deleted).

- One-off set-up: run `migrations/2026-10-22_outreach_queue.sql` in Supabase → SQL Editor.
  It creates `outreach_queue` and `outreach_runs`, the campaign (paused) and the wave-one
  queue. Safe to run again.
- Sends one at a time between 08:00 and 18:00 UK, Monday to Friday, up to
  `OUTREACH_DAILY_LIMIT` a day (default 50, ceiling 100), so it never looks like a burst.
- Pause/Resume, "Send me a test copy" and "Send the rest of today's batch now" are on
  Admin → Outreach. `OUTREACH_SCHEDULER=off` on Railway stops the timer without a deploy.
- Every email carries the app's unsubscribe link (needs `UNSUBSCRIBE_SECRET`) and
  one-click `List-Unsubscribe` headers. Bounces and complaints reported by Resend put the
  address on `outreach_suppressed` before the next send.
- Never set a row in `outreach_campaigns` to `active`: that is the old Node service's
  trigger word. The app's campaign uses `app_active` / `app_paused`.

## News and insights (admin sidebar)

`webhook/news.py` checks a short list of feeds and watched pages every three hours and lists anything new down the right-hand side of every admin page, with a full page at Admin → News (tag filter, hidden items, source status, Check now).

To switch on after deploying:

1. Run `webhook/migrations/2026-10-23_news.sql` in Supabase → SQL Editor (choose "Run and enable RLS"). It creates `news_items` and `news_sources`.
2. Nothing else: the first check runs two minutes after the app starts. Admin → News → Check now runs one immediately.

Sources are the `SOURCES` list in `news.py`: GOV.UK activity feeds for DESNZ, MHCLG and Ofgem (kept only when an entry mentions an assessment, retrofit, EPC, building regulations or related topic), the Elmhurst, ECMK and Quidos feeds (kept whole), and five watched pages with no feed (the GOV.UK SAP/Home Energy Model page, BRE's SAP 10 documents page, TrustMark news, gov.scot's EPC reform updates, SEAI's DEAP page), which each give one "Page updated" item when their content changes, at most once a week. A source that fails shows its error on the News page; the others carry on.

`NEWS_SCHEDULER=off` in Railway stops the checks without a deploy.

### Briefs

Clicking a news item opens a short brief in place: three to five bullet points and a "why it matters" line, written the first time the item is opened and saved on it. With `ANTHROPIC_API_KEY` set in Railway, Claude (claude-haiku-5-5) writes the brief from the article's own text; without it, the brief is the article's opening paragraphs. "Source ↗" opens the original. Run `webhook/migrations/2026-10-23_news_briefs.sql` once to add the brief columns (briefs still show without it, but are rewritten each time).
